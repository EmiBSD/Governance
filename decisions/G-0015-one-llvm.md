# G-0015: One LLVM, OpenBSD's, for the C and for rustc

Date: 2026-10-31 · Status: accepted · Binds: DevTools, Userland, Kernel

## Context
The decision of 2026-10-23 (recorded in G-0009 and in `rust/UPSTREAM.toml`) kept two LLVMs:
rustc 1.98.1 refuses an LLVM below 21 (`src/bootstrap/src/core/build_steps/llvm.rs`,
`check_llvm_version`: `need >=21`), and OpenBSD's `gnu/llvm` at the pin was believed to be
18.1.8, so rustc would build the LLVM of its own `src/llvm-project` submodule (rust-lang's
fork, 22.x) while the C kept OpenBSD's. On 2026-10-31, closing DevTools' T0, the version was
read from the source instead of from the note: OpenBSD's clang at the pin `3ce1f3f7` is
**22.1.6** (`gnu/usr.bin/clang/include/clang/Basic/Version.inc`). The premise of the two
LLVMs was wrong at this pin; the note had been copied from Userland into DevTools' pins
unverified, by the agent, and corrected the same day.

## Decision
The maintainer, 2026-10-31: one LLVM, from the fork; OpenBSD's copy is no longer a source
("para algo hicimos el fork; no me vengas a dejar duplicidad de herramientas con versiones
distintas"). The proposal below is the decided layout.

## Proposal
Build rustc against OpenBSD's LLVM 22.1.6 (`x.py` with `llvm-config` pointing at DevTools'
`llvm/` build and `download-ci-llvm = false`), the way distributions build rustc against a
system LLVM. One LLVM to build, patch and watch: the compiler of the C and the backend of the
Rust are the same binary, with OpenBSD's patches. The `src/llvm-project` submodule pin of `rust/UPSTREAM.toml` stays until T2 proves a Rust
hello under Kernel with this LLVM; then it is removed. The mirror stays: it is where the LLVM
now comes from.

## Where the one LLVM comes from (the maintainer's question of 2026-10-31)
From the fork, not from inside OpenBSD's tree. OpenBSD imports each LLVM release and commits
its changes on top, so its `gnu/llvm` at the pin is upstream `llvmorg-22.1.6` plus OpenBSD's
patches. The proposal makes that explicit:

- the mirror `EmiBSD/llvm-project` (already in LLVM's fork network) receives the upstream tag
  `llvmorg-22.1.6`; `llvm/UPSTREAM.toml` pins that tag with `origin = llvm/llvm-project`;
- OpenBSD's patches become `llvm/patches/`, a series generated by a script that diffs
  OpenBSD's `gnu/llvm` at the pin against the tag, per subproject (llvm, clang, lld, libc++,
  libc++abi, compiler-rt), so a pin bump regenerates it instead of re-deriving it by hand;
- the build glue (`gnu/usr.bin/clang`, `gnu/lib/libcxx*`, `libclang_rt`) still comes from
  `OpenBSD-src`, as the recipe, not as source.

So the diagram's arrow for the LLVM goes from the fork to DevTools, and from OpenBSD-src only
the patches and the glue. One mirror, one version, the patches visible and counted.

## Risks, named
- A patch series derived by diff must apply cleanly to the tag; the first derivation is the
  proof that OpenBSD's tree really is tag plus patches (a stray file is a finding).
- rust-lang's fork carries a few patches ahead of upstream; rustc's CI builds against system
  LLVMs, so a missing one shows as a test failure in T2, not silently.
- OpenBSD's patches (RETGUARD, `-fret-clean`, BTI and PAC defaults) are clang and codegen
  features; what they do to rustc's codegen on arm64 is to be measured at T2 with the hello
  and the smokes, not assumed.
- Each pin bump of OpenBSD may change the LLVM major; rustc's minimum follows. The watcher
  reports both.

## Consequences
G-0009's "two LLVMs" clause is superseded; DevTools' `CLAUDE.md`, `docs/TOOLCHAIN.md` and
`rust/UPSTREAM.toml` follow; `docs/architecture.md` here loses the "LLVM 21 that rustc builds"
box. T2 becomes cheaper by one multi-hour LLVM build.
